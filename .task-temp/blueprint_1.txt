1. Final Decision
This document freezes the architecture for a personal automated trading system. The goal is not to maximize agent count; it is to maximize reliable research, controlled adaptation, execution integrity and measurable learning per unit of complexity.
Personal single-owner automated trading system: optimize for reliable edge, not maximum framework count.
18 elite cognitive agents; only the agents needed for a task wake up. No 50-agent synchronous chain.
LangGraph orchestrates agent graphs. Temporal owns long-running recovery/promotion workflows.
Jev is a fast typed decision layer for classification/routing/triage; it is not an oracle and never owns capital authority.
NautilusTrader, Portfolio Engine, deterministic Risk Kernel and Execution Gateway own the live trading path.
Exness is the Priority-1 technical broker adapter through an isolated MT5 Gateway, but live enablement is gated by eligibility/compliance, health and instrument support.
Strategies never call broker SDKs directly. All brokers implement a canonical BrokerAdapter contract.
Every order path is idempotent, traceable, reconciled and linked to strategy/risk/decision identifiers.
Agent self-improvement creates immutable challenger versions; production versions are promoted only after offline eval, replay, shadow and canary gates.
Risk limits, kill switch, broker permissions, credentials and capital ceilings are non-self-modifying.

8. Hybrid Cognitive Engine: Jev + Deep Models
Jev is used only for fast typed classification/routing/triage where benchmarked. Deep models handle complex analysis, research, coding, repair and difficult disagreements. Deterministic code remains the first choice whenever a mathematical/rule-based answer exists.
Level 0  Deterministic math/rules -> risk, accounting, order stateLevel 1  Jev -> fast typed classification/routing/triageLevel 2  economical LLM -> routine reasoningLevel 3  frontier/challenger council -> uncertain or high-impact reasoning
Low confidence or disagreement escalates; it never becomes certainty by formatting.
Jev outage must have a safe fallback.
No model can authorize broker submission without RiskDecision.
Every model output has TTL, provenance, calibration hooks and trace ID.
9. Broker Architecture — Exness Priority, Not Dependency
Strategy -> TradeIntent -> Portfolio -> RiskDecision -> Execution Router                                      |                              Broker Capability/Policy                                      |                         +------------+------------+                         |            |            |                    Exness MT5       IBKR       Zerodha/other                    Priority-1
Exness lives behind an isolated MT5 Gateway; the main trading core does not embed MT5-specific logic.
Priority applies only if broker/instrument is enabled, healthy and allowed by configuration/compliance gate.
Existing positions are not transferred automatically across brokers.
Every broker has independent health, capability and reconciliation state.
Strategies use canonical instrument IDs; broker-specific symbol mapping is an adapter concern.
10. Agent Evolution Factory — Auto-Smarter, Controlled
Production traces/evals -> weakness detector -> root cause -> immutable challenger genome -> Jev/cheap pre-screen -> DSPy/optimization -> offline eval -> historical replay -> adversarial/security eval -> shadow -> canary -> promote OR rollback
Production agents never overwrite themselves.
Risk Kernel, kill switch, broker credentials, capital/leverage ceilings and order-idempotency logic are excluded from autonomous evolution.
Agent quality measures correctness, calibration, evidence freshness, reliability, latency, tool errors, cost and regime performance.
Continuous measurement; evolution is periodic and evidence-driven, not constant random mutation.
11. Failure & Recovery
NORMAL -> CAUTION -> REDUCED RISK -> NO NEW RISK -> FLATTEN ONLY -> HALTED
There is no direct HALTED -> NORMAL path. Critical recovery uses deterministic watchdogs plus Temporal workflows: diagnose -> repair candidate -> independent verification -> shadow -> canary -> reduced-risk -> normal.

17.2 Global safety UX
Operating modes: OFFLINE, BACKTEST, SHADOW, PAPER and RESTRICTED_LIVE are backend-authoritative.
Safety states: NORMAL -> CAUTION -> REDUCED_RISK -> NO_NEW_RISK -> FLATTEN_ONLY -> HALTED. Recovery follows backend policy; no direct HALTED -> NORMAL jump.
NO-NEW-RISK, FLATTEN-ONLY and HALT require deliberate confirmation, reason, re-authentication, idempotency and an authoritative backend receipt.
The UI never calls broker APIs directly and never owns authoritative P&L, risk, margin or reconciliation calculations.
Unknown, disconnected or stale state is shown explicitly instead of optimistically displaying healthy/live.
17.3 Realtime and control API
Initial state is loaded from versioned REST snapshots; realtime changes arrive through WebSocket/SSE envelopes containing schema version, sequence and timestamps.
Sequence gaps trigger a safe snapshot resync; stale values display age and a visible STALE state.
Every capital-affecting command returns a receipt ID, decision, authoritative resulting state, policy checks, server timestamp and trace ID.
Trace Explorer links market/event context -> agent decision -> strategy intent -> RiskDecision -> OrderCommand -> broker acknowledgement/fill -> reconciliation.
